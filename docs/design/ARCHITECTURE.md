# Engineering and architecture

## Runtime and presentation

The runtime uses Godot 4.6.3 and GDScript with Compatibility rendering, an orthographic Camera3D, Windows export, and single-threaded Web export. Use built-in primitives for structures and generate polygon geometry for territories. The prototype excludes C#, networking, navigation agents, terrain tooling, and complex third-party frameworks.

## State and simulation

Generate the region graph by clipping the map bounds around seeded Voronoi sites. Each cell has a stable ID, a polygon, and neighbors that share a border of positive length. The seeded sites follow a jittered grid across the long axis of the map. Consecutive sites share a border, so assigning starting territories from opposite ends of the traversal keeps each faction connected. The scene tracks ownership and resolves world positions to the nearest site inside the map bounds, breaking ties by site order. Track each side's resource stockpiles, income sources, owned regions, base HP, barracks count, upgrade, and timers. Track unit type ID, side, map-plane position, HP, attack cooldown, target, order, ordered destination, current movement destination, and remaining waypoints. Track simulation time and match outcome. Keep rules testable independently of rendering where practical, step shared combat deterministically with delta, and centralize balance values and CPU cadence.

`MatchEconomy` defines resources by stable ID, label, starting stockpile, and baseline rate. Each side holds its own stockpiles. A purchase validates every entry in its resource-to-amount cost before debiting stockpiles.

The match shares one `FactionStats` between economy and battle. Register a flat modifier with `set_modifier()` using a stable source ID and a stat key. Reusing that pair replaces its contribution. One source can contribute to several stats, and `remove_source()`, `set_source_owner()`, and `set_source_active()` update the whole source. Use `set_region_modifier()` for contributions that follow region ownership. Battle exposes source IDs for bases, outposts, and barracks so contributions can follow destruction or activation. Restart creates a fresh registry.

Income, unit DPS, damage per attack, movement speed, maximum HP, and barracks production expose computed totals with named source breakdowns. The registry adds the baseline first and then modifiers in lexical source ID order. Disabled entries retain their configured magnitude and contribute zero. Damage per attack scales each DPS contribution by the unit's attack interval. Units and destructible structures start at their effective maximum HP. Later cap increases preserve current HP, and decreases clamp it to the new cap. Barracks capacity expresses changes to the production cycle in units per second. Each completed cycle still requires its Food purchase.

The match scene exposes Legendary Landmarks settings for the count cap, per-region spawn probability, neutral-only eligibility, and weighted `LegendaryBuff` resources. The default cap is two initially neutral regions. The catalog adds one unit DPS, one resource per second, or ten maximum building HP. A dedicated stream derived from the active map seed chooses candidates and effects. The layout retains each landmark and its footprint across restarts, while the fresh stat registry registers each `legendary/<region>` source with the region's initial owner.

Producer catalog entries map resource IDs to per-second rates. Each placement registers its own structure ID and region in the stat breakdown. Producers share the destructible structure lifecycle with defenses, which disables their modifiers when territory is lost and removes them on destruction. The match accrues income on the same fixed steps as combat and unit purchases so changes to active sources take effect at the same simulation boundary.

The match indexes occupied footprints by stable structure ID in each covered region. The map's `region_building_capacity` setting defaults to five. Site previews, purchases, CPU site searches, claim eligibility, and landmark generation use the same capacity query. Walls register for inspection with a slot cost of zero. Neutral regions retain a slot for a claim outpost, and the Scout searches for an outpost site wholly inside its target region. Restart restores the index from the original bases and seeded landmarks.

Combat consumes elapsed time in fixed 60 Hz steps. Units plan from the same snapshot before movement and damage, and casualties are removed after all attacks for that step. The match scene projects pointer input to the same map plane and renders the battle state. Routes use direct segments or an AStar2D graph of building footprint corners, with clearance defined by the unit type. Changing a static obstacle invalidates cached routes. Units can overlap each other and static obstacles block line of fire. Unit state is available by ID through `MatchBattle.get_unit()` and by current selection through `selected_unit()` on the match scene.

The unit catalog defines provisional combat, Food, movement clearance and presentation values for Infantry, Ranged and Heavy. Each military building definition binds one stable unit type to its scene, footprint, construction price and baseline interval. Military producers share structure health, active territory checks and destruction cleanup. Each holds its own production timer and uses `MatchBattle.spawn_unit()` for paid deployments. Passing an economy charges the listed Food cost after the spawn site is validated. Ranged favors targets with a clear shot in range. Heavy has a configurable damage multiplier against structures.

The camera keeps its viewing angle fixed and moves its focus within the generated map bounds. Placement and battle navigation use the same bounds. Its zoom range runs from a close tactical view to an overview fitted to the projected map and HUD. Placement stores the map point at click time so camera movement before the next physics tick cannot move the purchase.

## Rules interfaces and validation

The proposed responsibility split gives match logic authority over purchases, claims, CPU actions, and end states. Shared battle logic handles spawning, movement, targeting, damage, and cleanup. Map visuals and HUD reflect state through the shared rules interface. Register each building type in the match catalog with its label, cost, visual scene, and purchase rules. The menu and placement logic read this catalog and use the same Voronoi lookup as region selection to resolve ownership at the cursor. Both factions dispatch through `dispatch_scout(faction, scout_id, region)`. Scout expeditions reserve eligible regions, track arrival and claim duration on battle steps, and hand completed claims to the ownership lifecycle. The match emits `claim_completed(faction, region, scout_id)` after it commits ownership and the outpost. Keep any browser instrumentation minimal and read-only. Cover initial ownership and adjacency, valid and invalid claims and purchases, barracks construction and production scaling, CPU actions, symmetric spawning, combat, outcomes, and reset in headless logic tests. A headless scene-load test checks initialization and gameplay on the expanded match. Use `res://tests/prototype_match_fixture.tscn` for capture setups that expect the original prototype coordinates.


The project starts at `game.tscn`, which opens match setup over the shared `main.tscn` gameplay scene. Confirming setup resets the existing match from its active map seed. The difficulty table in `match/difficulty_profile.gd` supplies CPU strategy weights, timing, and fixed search budgets relative to the scene's Standard settings. Decisions use the shared purchase and scout APIs.

Run `godot --headless --path . --script res://tests/match_cpu_difficulty_test.gd` for setup, reset, strategy and search budget assertions. Run `godot --headless --path . --script res://tests/match_cpu_difficulty_evaluation.gd` for paired seeded matches against scripted openings. Append `-- 1` through `-- 5` to evaluate a single level. The evaluation counts interrupted CPU expeditions as lost Energy, averages first-claim time over matches with a claim, reports the number of distinct CPU building types per match, and times strategy decisions separately from battle steps. It reports timeouts and includes them in the win-rate denominator.

## Narrative decisions

Assign a `NarrativeCatalog` to the match to define events by trigger ID, side, region, required facts and minimum stockpiles. The producer submits a stable occurrence ID to `narrative_events.submit()` with the trigger context. Reuse that ID for duplicate deliveries and across identical replays. The service selects an eligible definition by weight using the active map seed and the occurrence ID. Player decisions enter a FIFO queue. CPU callers use `resolve_cpu()` with an option ID or let the service score affordable choices by stockpile scarcity, short-term income and configured tactical utility. Ties use the match seed and occurrence ID. The service stores the selected option and rejects repeated resolutions.

Each event needs a choice with no resource cost so that earlier decisions cannot leave the player stuck. The dialogue uses the option descriptions and effect operations to show costs and rewards. The economy validates total spending before any grants or modifiers apply. Each modifier records the deciding faction and optional origin region. Positive durations count in battle time, and a zero duration keeps the modifier for the match.

A queued player decision raised during simulation opens at the end of the current fixed step. The modal pauses the scene tree across the entire queue. The match drops unused frame delta and carries forward the remaining CPU decision time. Restart replaces the event service, and a finished match dismisses pending decisions.

The production match subscribes to `claim_completed` after the claim has established ownership and the outpost. The claim occurrence ID uses the faction and stable region ID, so the service's recorded decision also serves as the match's claim discovery history. Reclamation by the same faction reuses its decision. Identical claims reproduce the original draw after restart with the same map seed. Landmark placement and bonuses use their own rules and seed stream. New trigger sources can submit their own occurrence IDs to the same service.
